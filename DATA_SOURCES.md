# Data Sources

## Summary

Everything in this project is **synthetic**. No production Razorpay customer or payment data was used, seen, or referenced anywhere in this build.

## Public dataset — investigated, not integrated

A public UPI transactions dataset (e.g. Kaggle's "UPI Transactions 2024") was considered as a source of realistic amount/timing distributions, per the buildathon brief's suggestion. It was not integrated: the sandboxed build environment's network access is restricted to package registries (PyPI, npm, GitHub) and does not extend to Kaggle or general web downloads. Rather than force a dataset in under that constraint or claim distributions were derived from it when they weren't, the existing hand-parameterized synthetic generator was kept as the sole data source, and this limitation is disclosed here and in the README rather than hidden.

## Synthetic data — what's generated and how

### Transactions (`backend/generate_data.py`)
200 synthetic failed payment records. Fields: `transaction_id`, `customer_id`, `amount`, `currency`, `payment_method`, `failure_code`, `failure_timestamp`, `attempt_count`, `status`, `customer_opt_out`, `last_action_timestamp`.

- Failure codes are weighted to loosely mirror real-world payment failure distributions (`insufficient_funds` and `bank_timeout` most common, `risk_block` rarest) — these weights are hand-set domain assumptions, not derived from any dataset.
- Amounts are bimodal: 85% small consumer payments (₹200-5,000), 15% larger (₹5,000-15,000).
- `payment_method` and `failure_code` are paired with a compatibility table so e.g. UPI never gets an "expired card" failure.
- `attempt_count` is pre-seeded (0-3, weighted toward 0) to simulate transactions with some pre-existing contact history, which then interacts with the real max-attempts policy rule during the pipeline run.

### Receivables (`backend/generate_data.py`)
400 synthetic overdue B2B invoices (increased from an original 50 during the production-hardening pass, specifically to fix a statistically underpowered baseline-vs-agent comparison — see README). Fields: `invoice_id`, `customer_id`, `amount`, `due_date`, `days_overdue`, `contact_history`, `status`, `customer_opt_out`, `attempt_count`, `last_action_timestamp`.

- `days_overdue` uniform over 7-90 days.
- Amounts uniform ₹10,000-500,000 (B2B scale).
- `attempt_count` derived from `days_overdue` (older invoices assumed to have had more prior contact attempts) — this is what causes many 60+ day invoices to correctly hit the max-attempts policy rule even before the agent runs.

### Checkout abandonments (`backend/generate_data.py`)
200 synthetic abandoned-cart records, added in the production-hardening pass to close the third revenue-risk category named in the buildathon brief. Fields: `session_id`, `customer_id`, `cart_value`, `abandoned_at`, `payment_attempted`, `customer_opt_out`, `attempt_count`, `last_action_timestamp`, `status`.

- Time-since-abandonment is the key axis, hand-set weights: 35% warm (<1hr), 40% cooling (1-24hr), 25% cold (>24hr) — same disclosure convention as the transaction/receivable weights above, not derived from any dataset.
- `payment_attempted` (never-started vs. attempted-then-left) is set independently, ~40% attempted; carts that reached a payment attempt skew somewhat higher-value, since the customer was more invested in the purchase.
- Cart values use the same consumer-scale distribution as transactions (₹200-15,000), since these are pre-payment consumer checkouts, not B2B invoices.

### ML training data (`ml/generate_training_data.py`)
~6,300 rows of (context, candidate action, outcome) triples across all three record types, generated by simulating **every** candidate action applicable to ~3,600 synthetic cases (not just the one actually executed), so the model has real counterfactual signal — e.g. it sees both what would happen if `bank_timeout` got `RETRY_NOW` *and* what would happen if it got `RETRY_LATER`, for the same underlying case.

**Important honesty note:** the base success rates used to simulate these outcomes are the same hand-set domain assumptions already encoded in `backend/execution.py`'s mock Razorpay/outreach layer (e.g. "bank_timeout retries succeed ~65% of the time"). Small feature-driven modifiers (time-of-day, attempt fatigue, invoice age, time-since-abandonment, and — added in the hardening pass — time-since-last-attempt) plus random noise are layered on top so the model has to learn a real pattern rather than memorize one constant per (failure_code/tier, action) pair — but fundamentally, this model is trained on outcomes drawn from parameters we ourselves set, not on discovered real-world data. It is a legitimate demonstration of ML methodology (real train/test split, no leakage, honest evaluation metrics, calibration checking) rather than a claim of predictive insight into real payment behavior.

## What's mocked (not synthetic data, but adjacent)

- **Payment execution** (`backend/execution.py`, `backend/agent_loop.py`): retries, payment links, reminders, cart-recovery/discount outreach are all simulated via probability tables (`MockExecutor`), never calling any real payment gateway or messaging service. A `PaymentExecutor` protocol makes this boundary explicit in code, with a deliberately unimplemented `RazorpayExecutor` stub documenting what a real integration would need — see README's Production Readiness section.
- **No API keys, secrets, or credentials of any kind are used or required anywhere in this project.** `.env.example` includes placeholder `RAZORPAY_API_KEY`/`RAZORPAY_WEBHOOK_SECRET` variables so the config is structured for a real integration to slot in later — both are empty by default and unused by any code path today.
